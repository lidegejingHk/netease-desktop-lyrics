# 网易云音乐 macOS 桌面歌词：设计

日期：2026-09-29

## 目标与范围

在 `/Users/linjingheng/netease-lyrics-rs` 新建独立 Rust 项目，只支持本机网易云音乐 macOS 客户端。按「验证播放数据源 → 歌词与同步引擎 → 悬浮歌词窗口」推进。第一阶段只做只读命令行验证程序；未经验证不开始窗口开发。

本机设计基线：Apple Silicon（arm64）、网易云音乐 `com.netease.163music` 3.1.12、Rust 工具链 1.95。只代表当前机器，不承诺其他版本兼容。

原项目 [Lensual/NeteaseMusicLrcHelper](https://github.com/Lensual/NeteaseMusicLrcHelper) 为 Windows UWP 助手，靠固定进程内存偏移获取歌曲 ID、播放进度，并按 ID 获取歌词。macOS 复用产品思路与 LRC 时序模型，不移植其 Windows 内存读取代码或固定偏移。

## 决策与备选

1. **首选：客户端本地状态／缓存（只读）。** 先确认 3.1.12 是否能提供当前歌曲的稳定标识、真实播放位置与播放／暂停状态。部分旧版本已有基于本地状态的社区方案，但文件布局和更新频率必须在当前版本实测，不预设存在 `lastPlaying` 或固定字段。
2. **备选：macOS 辅助功能（Accessibility）。** 若本地状态缺必要字段，验证客户端 UI 能否读取曲目信息和进度；明确提示用户授权，并记录窗口关闭、界面改版或控件不可见的局限。若只有歌名而无唯一 ID，不能直接当成可靠的歌曲匹配。
3. **不作为首版方案：进程内存偏移、注入、未公开的系统媒体私有接口。** 兼容成本高且易受更新影响；也不把 `MPNowPlayingInfoCenter` 误用为读取其他 App 的通用 API。

若两种只读数据源都不能稳定获取歌曲标识、进度和播放状态，第一阶段输出具体缺项与诊断结论，停止进入歌词同步和 UI；另行讨论扩展方案。

## 组件与数据流

- `PlaybackSource`：隔离网易云版本相关探测，返回 `PlaybackSnapshot { track_id, title?, artist?, position_ms, is_playing, observed_at }`。字段缺失显式报告；不把猜测的时间伪装成实测值。
- `LyricsProvider`：按 `track_id` 拉取原文和译文，缓存结果；歌词接口以实际请求验证为准，不假设历史地址长期稳定。无歌词、网络错误与解析失败分别处理。
- `LrcEngine`：独立解析 `[mm:ss.xx]` 等时间标签、同一行多时间标签、偏移和翻译；排序并计算当前行。播放中依据最近一次可信进度和单调时钟推进，暂停冻结；跳转或新快照偏差明显时重校准。
- `LyricsWindow`：仅在前两项验证后开发。Rust 核心提供当前行状态；macOS AppKit 窗口负责透明、置顶、点击穿透、单／双行及翻译显示。窗口实现不反向依赖数据源格式。

数据流：网易云客户端 → `PlaybackSource` → 歌曲变更触发 `LyricsProvider` → `LrcEngine` 根据进度选行 → 终端输出（第一阶段）／悬浮窗（最后阶段）。网络或源失效时显示明确的不可用状态，不沿用旧歌歌词。

## 第一阶段交付与验收

1. 项目只在上述独立目录内写入；初始化独立 Git 仓库，不触碰原项目和网易云客户端数据。
2. CLI 只读观察本机网易云 3.1.12；能区分未运行、无歌曲、字段缺失、权限不足、格式变化等状态。默认不持久化用户播放数据、令牌或缓存原文。
3. 在本机手动做「启动／退出、切歌、暂停／恢复、进度拖动、上一首／下一首」测试，记录每一步的歌曲标识、进度和状态是否实时、准确。验收要求：切歌可区分歌曲；暂停不假推进；跳转可观测并重校准。记录实测延迟，而非预先承诺某个毫秒精度。
4. 源读取逻辑与时间模型使用可重复的模拟输入做单元测试；对无法自动化的网易云行为保留手工验收清单。
5. 第一阶段完成后给出「可继续／受限继续／不可继续」结论。只有完整满足标识、进度、播放状态条件才按当前设计推进自动歌词同步。

## 后续阶段边界

第二阶段加入歌词请求、缓存、LRC 解析和同步测试，先保持 CLI；第三阶段接 AppKit 悬浮窗与交互测试。首版不做登录、控制网易云播放、开机启动、多播放器兼容或歌词内容分发。

本设计先等用户审阅确认，再写实施计划和 Rust 代码。每次代码改动完成并验证后提交 Git commit。
